## 四、面试必答题预测（结合前几场教训）

1. **「Verilog 代码质量怎么自动评估？」** → 双闸：综合（语法+可综合性）+ 仿真（功能对错），等价于我代码项目里的「编译+测试」沙箱，且更硬——没有运行时不确定性
2. **「RTL 上做 GRPO 和通用代码后训练有什么不同？」** → 三点：奖励更可验证（仿真不撒谎）；序列长、格式约束强（module 结构）；数据更稀缺（公开 RTL 数据量远小于通用代码）——所以数据工程和评估 pipeline 是 JD 的前两条
3. **「DPO 偏好对怎么构造？」** → 同一 spec 的两个候选实现，用综合+仿真结果排序（都过仿真时比综合资源/代码风格），必要时人工补充——等价于我 verifier 数据的「沙箱自动标注 + 少量人类解答加权」
4. **「你为什么投 RTL 方向？」** → 本科自动化懂硬件 + 代码强化学习做过完整管线 + RLVR 在 RTL 上是完美场景——想在这个交叉点上做深
5. 前几场的通用题（显存账、GRPO/PPO、奖励黑客、verifier 细节）照常准备——面试官大概率还会问项目

## 六、零基础名词解释（速成前先看这一节）

- **spec→RTL**：自然语言规格 → Verilog 代码的任务（与「题目→Python」同构，目标语言换成硬件描述语言）。spec =「写一个 8 位计数器」；RTL = 对应的 module 电路描述。RTL 描述的是电路（信号并行、时钟驱动），编译叫「综合」。
- **Yosys + Verilator**：开源综合工具 + 开源仿真器 = RTL 的「编译 + 跑测试」。两道闸门：综合通过 = 语法对、电路可实现；仿真通过 = 功能对。两道都要过才算对（语法对但逻辑错的代码：综合过、仿真挂；不能综合的连仿真都跑不了）。两者就是 RTL 模型的主奖励来源（天然可验证 = RLVR 完美场景）。
- **评估脚本 vs verifier 的区别（面试可能问）**：评估脚本 = 真实执行的裁判（调用 Yosys/Verilator 判对错，对应代码项目的沙箱+评测流水线）；verifier = 训练出来的预测模型（给连续概率，软信号）——主裁判永远是真实执行，verifier 只是辅助，正是项目里的主从设计。
- **MS-Swift / LLaMA-Factory**：开源微调全家桶框架（SFT/DPO/GRPO 封装成配置+一条命令）。LLaMA-Factory 最流行；MS-Swift 是阿里 ModelScope 生态。原理同源 veRL，跑一个 demo 即可说会用。
- **RTLCoder / VeriCoder / VeriRL / ChatSVA**：RTL-LLM 前沿谱系——RTLCoder（2023，SFT 路线开山）、VeriCoder（2025，更强数据）、VeriRL（2025，仿真当奖励的 RL 路线 = RLVR 落地）、ChatSVA（断言生成）。
- **SVA / Bug Detection**：SVA = SystemVerilog Assertion，写在电路代码里的「必须成立的条件」（如 assert counter < 100），仿真时自动检查违反；Bug Detection = 用模型找 RTL 硬件 bug（位宽/时序/竞争）；SVA 能被仿真验证 → 又是可验证奖励场景。
